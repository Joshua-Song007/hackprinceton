## Debugging: do this yourself before asking a human
Diagnose in writing: for every failure, read the log, name the root cause, and post a comment on the PR or issue with symptom, cause and fix plan before you relaunch or change anything.
Worker logs are in `../logs/<slug>.json` (fields `result`, `is_error`, `subtype`, `permission_denials`) and `../logs/<slug>.log`; read them with the Read tool.
- **CI red on your PR:** `gh pr checks <n>`, find the run with `gh run list --branch <branch>`, read `gh run view <run-id> --log-failed`, then relaunch the worker with the failing lines pasted into its task.
- **Behind main or conflicting:** if the conflict is mechanical and the PR is yours, relaunch the worker with: `git fetch origin, git merge origin/main, resolve conflicts keeping both sides' intent, run the verify script, push.` Otherwise step 2d.
- **Worker ended without a push:** read its JSON. `permission_denials` set: open the `[permission]` issue. `subtype` `error_max_turns` or `error_max_budget_usd`: relaunch once with a smaller scope, then `[stuck]`.
- **Reviewer says CHANGES NEEDED:** relaunch with the findings; at most 3 rounds (step 7).
- **Flaky CI:** `gh run rerun <run-id> --failed` once; fails again: label `flaky` and open an issue.
- **`main` red after a merge:** open a `[ci]` issue with the failing job link and fix it through a PR.
- **Usage or rate limit:** the cycle fails and `loop.sh` backs off; do nothing.
- **Dirty worktrees:** run `cleanup.sh`. A stale `../.setup.lock` needs a human to `rmdir` it (`run.sh` stops with a message after 2 minutes).

## Permissions
Tien's decision: orchestrators run locally on their laptop with full GitHub access (`gh`: PRs, reviews, comments, issues, labels, API), may push any branch except `main`, and may force-push their own branches. Still denied: editing `.claude/`, `CLAUDE.md`, `.agents/`, `.github/`, `gh repo delete`, `gh secret`, `gh ssh-key|gpg-key`, `git reset|rebase|checkout|restore`, `rm -rf`, `sudo`, `curl`, `wget`. Permission is not the default flow:
- Every change to `main` is a squash merge of a PR from a branch (`gh pr merge <n> --squash`). Never push `main` directly, even when `main` is broken: fix it through a PR. `settings.orch.json` denies `git push` to `main`.
- Force-push only with `--force-with-lease` and only on branches you created. Never rewrite history that another laptop has already pulled.
- Every force-push gets one line in the `Agent status` issue: what, why, the commit before and after.

## Escalation
Full table in `.agents/LOOP.md`.
- A change to `overview.md`, to a package boundary, to scope, or a hard-to-reverse choice: open an issue labeled `needs-tien` and `contract-change`. While it waits, take the smallest reversible default, mark it `[provisional: needs-tien-review]`, and keep moving on other items.
- A script, cleanup or CI problem you cannot fix yourself (a command misbehaves, a check is wrong or flaky, you want a helper): open an issue labeled `tooling` with the exact command and output. The integrator (`.agents/INTEGRATOR.md`) reads those issues and fixes the scripts and workflows; you never edit them.
- A `DECISION:` comment from Tien on an issue overrides everything.
- Conflicts between PRs or with `main`: step 2d (review, open a `conflict` issue for the other owner, `RESOLUTION:` comments). Still stuck after one round: the lead for that issue number decides (Lead orchestrators section).
